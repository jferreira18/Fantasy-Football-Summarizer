# ESPN Fantasy League Intelligence Agent

## Product Requirements Document

**Version:** 1.0
**Target Season:** 2026 ESPN Fantasy Football
**Primary Language:** Python
**Primary Interface:** Automated weekly email
**Execution:** Every Tuesday morning
**Design Principle:** Python calculates. The LLM interprets. Email delivers.

---

# 1. Product Overview

Build an automated Fantasy Football League Intelligence Agent that connects to an ESPN Fantasy Football league, retrieves league data, performs deterministic statistical analysis in Python, generates a detailed narrative using an LLM, and automatically emails a weekly league report every Tuesday morning.

The system should function as an automated fantasy league analyst.

It should go beyond ESPN's standard weekly recap by identifying interesting matchups, waiver activity, standings movement, manager behavior, scoring trends, schedule effects, lineup efficiency, and unusual statistical events.

After deployment, normal weekly operation should require no human interaction.

The high-level pipeline is:

```text
Tuesday Morning Scheduler
          │
          ▼
     ESPN Fantasy API
          │
          ▼
    Data Normalization
          │
          ▼
   Historical Storage
          │
          ▼
 Python Analytics Engine
          │
          ▼
 Structured Analysis JSON
          │
          ▼
        LLM
          │
          ▼
 Markdown + HTML Report
          │
          ▼
        Email
```

---

# 2. Product Goals

The system must:

1. Automatically run every Tuesday morning.
2. Determine the most recently completed ESPN fantasy scoring period.
3. Retrieve the required ESPN league data.
4. Normalize ESPN's API responses into stable internal data structures.
5. Maintain historical weekly snapshots.
6. Perform ALL mathematical/statistical analysis in Python.
7. Select the week's three most noteworthy matchups algorithmically.
8. Analyze waiver claims, free-agent moves, FAAB spending, and trades.
9. Identify league-wide and team-specific trends.
10. Analyze standings movement and schedule effects.
11. Detect unusual or noteworthy events.
12. Generate a detailed narrative using an LLM.
13. Generate Markdown and HTML versions of the report.
14. Automatically email the HTML report.
15. Prevent duplicate weekly reports.
16. Preserve sufficient structured data to audit every numerical statement generated by the LLM.

---

# 3. Non-Goals

The initial version does NOT need to:

* modify ESPN rosters
* submit waiver claims
* propose or execute trades
* manage lineups
* scrape the ESPN website UI
* embed directly inside ESPN
* predict player performance
* replace ESPN as the league system of record
* depend on Codex being active

Codex is the development environment/agent used to build the application.

The production application must operate independently.

# 4. Core Architectural Rule

Maintain strict separation between data, analytics, interpretation, and presentation.

```text
ESPN

 ↓
FACTS

DETECTION
SELECTION

LLM
 ↓

 ↓

```

The LLM must NEVER be responsible for calculating a numerical statistic.

If the LLM needs a statistic that does not exist, add the calculation to Python.

Python is the analytical source of truth.

# 12. Top Three Matchups

Python—not the LLM—must select the week's three most interesting matchups.

Create a deterministic and documented `interest_score`.

Potential components include:

```text
close score
high combined scoring
high-scoring loss
projection upset
standings implications
season implications
unusual bench performance
unusually high/low scoring
historical significance
```

Normalize metrics where necessary so one component does not dominate solely because of scale.

Example:

```json
{
  "rank": 1,
  "interest_score": 8.7,
  "reasons": [
    "closest matchup of the week",
    "second-highest combined score",
    "losing team had third-highest score of week"
  ]
}
```

The LLM receives these matchups and explains why they mattered.

It does not select them.

# 23. LLM Role

The LLM is the league's REPORTER and ANALYST.

It is not the calculator.

System prompt concept:

```text
You are the weekly analyst for an ESPN Fantasy Football league.

All numerical analysis has already been performed by Python.

Never independently calculate statistics, rankings, averages,
differences, probabilities, or other numerical metrics.

Use only facts contained in the supplied analysis object.

Never invent injuries, player performance, transactions,
manager motivations, league events, or statistics.

Your job is to identify the most interesting stories contained
in the supplied data and explain them clearly.

Prioritize meaningful insights over repeating every available
statistic.

You may make qualitative observations when they are directly
supported by supplied metrics.

Distinguish interpretation from factual statistics.
```

# 24. LLM Narrative Style

The weekly report should feel like a combination of:

* fantasy football analyst
* sports columnist
* league beat reporter

The tone can be entertaining and conversational.

It should NOT merely transform JSON into sentences.

The LLM should synthesize multiple Python-generated metrics into useful observations.

For example:

Bad:

```text
Team A scored 141.
Team B scored 137.
Team A won by four.
```

Better:

```text
Team A escaped the week's closest matchup, edging Team B
141–137. Team B's 137 points were still the fourth-highest
total in the league, making the loss particularly costly.
```

Every number in the latter example must already exist in the analysis object.

# 30. Completed-Week Detection

Never assume:

```text
calendar week == ESPN scoring period
```

At startup:

1. Connect to ESPN.
2. Query league status.
3. Identify the most recently COMPLETED scoring period.
4. Check whether it has already been processed.
5. Exit if the report was already successfully delivered.
6. Otherwise process that week.

This protects against ESPN schedule variations and postponed games.

# 37. Failure Handling

The weekly job must fail safely.

## ESPN Failure

If ESPN data cannot be reliably retrieved:

```text
ESPN_FETCH_FAILED
```

Do not generate a partial report.

Do not email.

Do not mark the week complete.

---

## Analytics Failure

If Python analytics fail:

Do not invoke the LLM.

Preserve retrieved data for debugging.

---

## Validation Failure

If required analysis fields are missing or inconsistent:

Do not invoke the LLM.

Log the validation problem.

---

## LLM Failure

If the LLM is unavailable:

Preserve:

```text
raw data
normalized data
analysis JSON
```

Allow report generation to be retried without re-fetching ESPN.

---

## Email Failure

If email delivery fails:

Preserve the generated report.

Do not rerun analytics unnecessarily.

Retry email delivery independently.

Do not mark the week complete until delivery succeeds.

# 49. Success Criteria

The system is successful when a league member can receive an email every Tuesday morning containing information that is meaningfully more insightful than ESPN's standard scoreboard.

The report should answer:

```text
What happened?

Which games actually mattered?

Why were they interesting?

Who made important roster moves?

Did those moves work?

Who is trending upward/downward?

Who is performing better/worse than their record?

Who is spending FAAB effectively?

Who has faced an unusually difficult/easy schedule?

What unusual event happened this week?

What story is developing across the league?
```

without requiring the recipient to manually inspect the league.

# 51. Primary Engineering Principle

When deciding where new functionality belongs, use this test:

**Does it require determining a fact?**

→ Python.

**Does it require calculating or comparing something?**

→ Python.

**Does it require ranking or selecting something?**

→ Python.

**Does it require detecting whether something unusual occurred?**

→ Python.

**Does it require explaining why those facts are interesting in natural language?**

→ LLM.

**Does it require making the result easy to consume?**

→ Report/email layer.

Never move deterministic analytical responsibility into the LLM merely because doing so is easier.

The goal is a system whose analysis is reproducible, testable, auditable, and increasingly valuable as historical league data accumulates.
